# BirdieBuddy — 현호P 개발 실행 계획

> **카드 UI 후속 인계:** [목록·상세·강화 변경과 담당자별 연결 사항](./card-ui-handoff.md)을 먼저 확인합니다. 사용자 지시로 이번 단계의 API 연결은 제외했습니다. 장수·수집 현황·강화 결과는 목업이며 실제 데이터나 서버 성공으로 취급하지 않습니다.

> **실제 카드 이미지 인계:** [R2 CDN 주소·DB/프론트 적용 지침](./card-assets.md), [36개 이미지 JSON 목록](./assets/card-images.json)을 사용합니다. 선수 식별자 12개·3등급이며 최종 이미지는 R2 출처입니다. 기존 Supabase Storage URL 생성·스타일 기반 경로를 그대로 적용하지 않습니다. DB·SDK·화면 연결은 아직 별도 작업입니다.

> **디자인 시스템 적용 인계:** 화면·공통 UI 작업 전 [에이전트 적용 가이드](../design-system/AGENT_GUIDE.md)를 확인합니다. 최신 원본·적용 상태·샘플 전용 구성·담당 경계와 검증 기준을 정리했습니다. 실제 API 연결을 보존하고 이전 카드 정의를 신규 요구사항으로 복제하지 않습니다.

**담당:** 카드 화면·강화 연출·전체 화면 디자인·별도 카드 디자인 프로젝트와 A-06 연계. 카드 뽑기 연출은 2026-11-13 `/draw/preview` 시안으로 확정.

**최종 갱신:** 2026-11-13

**상태:** 카드 기준을 스타일 없음·4유형·3등급으로 변경했습니다. 디자인 시스템 보강·공통 상태 샘플·기본 프로필 에셋은 커밋되어 있으며, 새 카드 계약의 실제 구현 전환은 미완료입니다.

## 최신 카드 기준과 다음 작업 (2026-11-12)

이 절과 [카드 변경 명세·담당자 인계](./card-spec.md)를 아래 이전 실행 계획보다 우선합니다. 사용자가 언급한 현호P 문서는 이 파일입니다.

- 디자인 스타일은 없습니다. `illust/retro/holo` 선택·표시·필터·수집 보너스를 신규 요구사항으로 사용하지 않습니다.
- 카드 유형은 `kpga`, `klpga`, `gtour`, `media`의 4개입니다.
- 등급은 `basic`, `rare`, `legend`의 3개이며 BASIC → RARE → LEGEND 순입니다.
- 최종 카드 path는 **`<유형>-<선수명>-<레벨>.png`**입니다. 예: `gtour-gong_tae_pung-basic.png`. 레벨은 등급과 같으며 실제 PNG 파일을 사용합니다. 스타일·UUID·제작 버전 문자열을 임의로 붙이지 않습니다.
- 실제 제작 목록을 기준으로 카드 수·파일 수·인물별 유형과 등급을 검수합니다. 기존 인물10명×스타일3종=30장 목표는 폐기합니다. 최종 개수는 미확정입니다.
- 새 계약에 맞는 카드 상세·강화 화면, 배지·필터와 뽑기 연출을 준비합니다. 기존 SDK와 UI가 이미 새 계약을 지원한다고 가정하지 않습니다.
- 홍주P에게 데이터 모델·SDK·이미지 경로·기존 데이터 이관, 문환P에게 3등급 확률·발급·스타일 의존 계산, 자성P에게 새 계약의 화면 연결을 인계합니다. 세부 작업과 미정 항목은 공통 명세를 따릅니다.

### 현호P 확인·결정 (2026-11-13)

- **3등급 발급 확률:** 문환P 제안 B안 **BASIC 70% · RARE 27.5% · LEGEND 2.5%**에 동의합니다(`문환P_plan.md` 3절). 홍주P와 제품 담당의 확인은 별도입니다.
- **보유 배지·보유 점수:** 문환P 제안에 동의합니다. 버디는 같은 인물 누적 10장, 이글은 누적 15장 또는 LEGEND 보유, 알바트로스는 누적 15장 그리고 LEGEND 보유입니다. 보유 점수는 배지 점수에 보유 최고 등급 RARE +5, LEGEND +10을 더합니다. 배지 3종의 모양과 표시 위치는 그대로이므로 시안 변경은 없고, D-10 시안의 조건 문구만 이 기준을 따릅니다.
- **카드 데이터 조회와 상세 범위:** 보유 카드 목록·상세·강화는 보유 카드 목록 데이터(`getOwnedCards` 계열)를 씁니다. 상세는 보유한 카드만 제공하고, 미보유 카드는 컬렉션에서 눌리지 않으며 0장 상세 주소는 보유 카드 목록으로 이동합니다. 등급 줄의 미보유 등급은 보이되 누를 수 없고, 강화 결과는 새로 받은 등급의 상세로 이동합니다. 목업에 적용했습니다([card-ui-handoff.md "카드 상세 규칙"](./card-ui-handoff.md)). 등급별 이미지·3등급·유형 4개를 담은 새 조회 계약은 홍주P 서버 작업 뒤 연결합니다.
- **뽑기 연출:** `/draw/preview` 시안을 이대로 확정합니다. 시간값은 `lib/cards/presentation.ts`의 `drawRevealTiming`(떠오름 0.6초, 박동 0.8초 × BASIC 2·RARE 3·LEGEND 4회, 6초 뒤 자동 공개, 뒤집기 0.7초)입니다. 새 3등급 SDK가 나오면 `/draw` 결과를 `CardDrawReveal`로 감싸고 미리보기 링크와 `/draw/preview`를 정리합니다.
- **선수 한글 표시명 12명:** 확정했습니다([card-assets.md "선수 한글 표시명"](./card-assets.md)). 화면 목업에 반영했습니다. 인물 UUID 매핑과 기존 등급 이관은 아직 정하지 않았습니다.

### 카드 상세 UI 목업 구현 (2026-11-12)

- `/collection/[cardId]` 독립 페이지와 카드 없음 화면을 추가했습니다. 현재 진입 예시는 `/collection/c1`, `/collection/c2`, `/collection/c3`입니다.
- 홈·컬렉션·보유 카드 탭의 목업 카드 링크로 진입합니다. `?from=owned`로 진입하면 보유 탭으로 돌아갑니다.
- 선수·등급별 실제 아트와 DB는 연결하지 않고 보유 카드에 공통 목업 이미지 `https://pub-6f54ef3ca9cb44659b6f40ae35e9c7ad.r2.dev/default-card-at.png`(`lib/cards/presentation.ts`의 `previewCardImageUrl`)를 사용합니다. 미보유 카드는 실루엣을 유지하고 이미지 실패 시 실루엣으로 대체합니다. 상세에는 유형·3등급·장수·조건부 인증 배지·강화 안내를 표시합니다. 목업의 인증 값은 null이며 인증 배지를 임의로 부여하지 않습니다.
- 홈·컬렉션 공용 UI 목업은 스타일 없이 basic/rare/legend와 새 유형으로 갱신했습니다. 기존 서버 등급을 변환하지 않습니다.
- 강화는 `/collection/upgrade?cardId=<cardId>`로 진입하는 확인·결과 목업을 추가했습니다. 시안 비용 10장으로 소모·획득·잔여를 확인하고 결과를 미리 봅니다. 실제 요청·수량 소모·저장은 하지 않으며 부족 수량·최고 등급·유효하지 않은 카드 주소를 처리합니다.
- c2 BASIC 목업은 확인·결과 화면 체험을 위해 보유 11장으로 준비했습니다. 결과는 화면 내 일시적인 계산이며 복귀·새로고침 시 초기화됩니다. 결과 제목 포커스와 `from=owned` 복귀를 지원합니다. 확인 후 기본 강화 연출(카드가 모인 뒤 다음 등급 공개, RARE 약 3초·LEGEND 약 5초 시안)·건너뛰기·동작 줄이기 시 즉시 결과·이탈 시 타이머 정리를 구현했습니다. 실제 서버 확정 이후 연출 연결·재시도·멱등 처리는 미구현입니다.
- 상세에 같은 카드의 등급 전환(등급별 수량·미보유 표시)과 0장 등급의 미보유 표시를 추가했습니다. 강화 확인·결과에 다음 등급 기존 수량과 결과 수량, 입장 자격·보유 배지·누적 획득 유지 안내를 표시합니다. 컬렉션 전체 미보유 시 라운드 완료 안내를 표시합니다.
- 실제 인물/템플릿 UUID·등급별 보유 수량·인증·설정 비용은 후속 SDK 연결 때 서버 응답을 사용합니다. 목업의 12종 표시는 현재 에셋 목록을 참고한 예시이며 DB 템플릿 수 확정이 아닙니다.

### 카드 목록 UI 정비 — 사용자 요청으로 API 연결 보류

- `/collection`과 `/collection/owned`를 분리하고 기존 owned 탭 URL은 보유 경로로 이동합니다.
- 2026-11-13 사용자 결정: 컬렉션(`/collection`)은 도감(선수×등급 36장, 실제 아트, 미보유 흑백), 보유 카드(`/collection/owned`)는 실제 데이터 화면으로 역할을 나눴습니다. 지금의 `getCollection`은 예전 규격이라 컬렉션은 **당분간 정적 목록(manifest)** 을 쓰고, 홍주P의 새 3등급 `getCollection`(선수 12명×3등급·유형 4개·등급별 이미지)이 나오면 카드 목록을 API로 전환합니다. 전환 뒤 조회 실패는 오류·다시 시도로 표시합니다. 전환 후에는 PRD의 컬렉션 정의와 같아지므로 PRD 수정 요청은 하지 않습니다.
- 목록 필터를 select 그리드에서 디자인 시스템 칩·정렬 토글·현황 패널로 교체했습니다.

### 채팅 읽음 상태 시안 (2026-11-13, 자성P v3 §3.5 요청)

- "여기까지 읽었어요"의 구분선·안 읽은 수 배지(99+)·NEW 배지·"최신 메시지로" 버튼을 `design-system/chat.css`(`.bb-read-divider`·`.bb-count-badge`·`.bb-new-badge`·`.bb-jump-latest`)로 만들었습니다. foundation 페이지의 "읽음 상태" 절과 `sample/chat.html`·`sample/screens.html`(채팅방 목록·인박스)에 반영했습니다.
- 자성P 코드의 임시 클래스를 교체하는 표는 `design-system/DEVELOPMENT.md`에 있습니다. 자성P 파일은 수정하지 않았습니다.
- 자성P v3 §4 요청에 따라 쓰지 않는 예전 카드 목업 스타일(`card-picture`·`portrait`·`peach`·`lavender`·`empty`)과 `--art-*` 토큰을 삭제하고, 정적 시안의 초상화 자리표시자를 실제 카드 PNG로 교체했습니다.

### 뽑기 연출 목업 (2026-11-13)

- 사용자 결정: 뒷면 카드 두근두근 박동 → 탭해서 3D 뒤집기, 등급 암시(박동 BASIC 2·RARE 3·LEGEND 4회, 흰빛·붉은 빛·골드, RARE 이상 반짝임, LEGEND 플래시·광택), 별도 목업 경로 `/draw/preview`.
- 순서: 떠오름(0.6초) → 두근두근(박동당 0.8초) → 탭 대기(6초 뒤 자동 공개) → 뒤집기(0.7초) → 결과(NEW/+1장·LEVEL 트랙·보유 장수·입장 안내·이동). 건너뛰기·동작 줄이기·진동 지원.
- 자성P의 `/draw`(이전 규격 API 연결)는 수정하지 않았습니다. 새 3등급 SDK 전환 시 `/draw` 결과를 `CardDrawReveal`로 감쌉니다. 목업은 실제 발급·추첨·수량 변경을 하지 않습니다.
- 전체 목록은 제공된 선수 식별자 12개를 재사용한 템플릿 목업이며, 미보유·등급별 수량을 포함합니다. 보유 목록은 양수인 템플릿×등급만 표시합니다. 모든 수집 수치와 장수는 목업에서 계산하고 실제 수량처럼 표시하지 않습니다.
- 선수/유형/등급 필터, 기본 등급순·장수순 정렬, 목록 강화 가능 표시, 등급별 상세·강화 이동과 0장 제외를 구현했습니다.
- 로딩·오류/재시도·등록 없음·전체 미보유·필터 결과 없음 표시를 구분하며 실제 조회·강화 후 동기화는 미구현입니다.
- 서버 조회 API는 존재하지만 기존 스타일·4등급 계약이므로 연결하지 않습니다. 사용자가 명시적으로 이번 API 연결을 제외했습니다. 실제 DB·SDK·권한·확률·이관은 변경하지 않습니다.

### 팀 진행 상황과 현재 브랜치 구분

사용자 공유 기준으로 백엔드·AI는 main 반영, 자성P 화면은 실제 Supabase 로그인·API 연결 상태입니다. 관리자 데모 월 연결·전체 흐름 점검·배포가 남아 있습니다. 이는 팀 진행 상황 공유이며 현재 작업 브랜치 코드의 통합 검증 결과가 아닙니다. 현재 브랜치 홈·컬렉션에는 목업이 남아 있으므로 자성P 최신 화면과 중복 구현을 피하고 통합 지점을 확인합니다.

현호P의 남은 핵심 작업은 카드 상세의 실제 SDK 연동·강화, 제작 카드 아트의 최종 검수·전달, 뽑기 연출 결정과 새 카드 기준의 디자인 통합입니다. 원격 재배포·데모 암호 교체는 홍주P, 시연 대본·리허설은 담당 미정입니다.

## 이전 실행 계획 — 변경 영향 확인용

아래 0~7절은 이전 3스타일·4등급 설계를 포함합니다. 기존 구현의 배경·오류 처리·담당 경계 확인용으로 보존하며, 카드 규격·개수·확률·스타일 보너스·강화 등급은 최신 명세로 대체합니다. 과거 체크리스트를 새 요구사항으로 그대로 실행하지 않습니다.

## 0. 실행 기준과 시작 방법

사용자가 현호P 개발을 시작하라고 요청하면 실제 파일과 아래 티켓을 대조해 미완료 작업부터 진행합니다. 이번 요청은 계획 갱신이며 앱·설정·이미지·환경 파일을 미리 생성하지 않습니다.

1. 작업 지침·기존 수정사항·F-01 골격·SDK 존재를 확인합니다. 기존 사용자 변경을 보존하고 현호P 담당 경로를 필요한 범위에서 수정합니다.
2. [디자인 가이드](./design.md)에 따라 앱 화면을 구현하고, 카드 디자인과 A-06은 별도 프로젝트에서 진행합니다. 뽑기 연출은 결정 전까지 구현 사양으로 취급하지 않습니다. 기존 프론트를 사용하고 별도 앱 서버를 추가하지 않습니다.
3. B-03·B-04 SDK가 준비되면 더미 공급부를 교체합니다. 발급·강화 성공, 거부, 결과 미확정, 계정 전환을 검증하고 T-03에 연결합니다.

5. 변경 파일·검증 명령·결과·미검증 범위·다음 작업을 기록합니다. 더미 UI, 실제 SDK, 최종 이미지, 팀 화면 통합, 원격 배포는 각각 구분합니다.

## 2. 제품 규칙과 화면 실행 명세

### 2.1 용어·수량·식별

- **발급**은 서버가 라운드 1회당 카드 1장을 확정하는 동작이고, **뽑기 연출**은 확정 결과를 공개하는 효과입니다. 건너뛰기·이탈로 발급 결과가 바뀌지 않습니다. 시연에 미개봉 카드팩은 없습니다.
- **카드 템플릿**은 인물×스타일 30종, **카드**는 템플릿×등급입니다. 장별 ID 없이 수량으로 관리합니다. drawId는 **발급 기록** ID이며 카드 개별 ID가 아닙니다.
- **컬렉션**은 미보유 포함 전체 템플릿, **보유 카드**는 현재 1장 이상인 template×grade입니다. 도감·인벤토리 등으로 혼용하지 않습니다.
- **누적 획득 장수**는 라운드 보상 발급 기록 기준으로 강화해도 줄지 않습니다. 현재 수량으로 역산하지 않습니다. isNew는 발급 직전 해당 템플릿의 전체 등급 현재 수량이 0인지입니다.
- 등급 common/rare/epic/special은 일반/레어/에픽/스페셜, 스타일은 illust/retro/holo, 유형은 youtuber/media_pro/tour입니다. 등급은 색상과 이름·아이콘으로 구분합니다.

### 2.2 화면별 조작·필수 상태

| 화면 | 조작·표시 | 필수 상태·완료 기준 |
| --- | --- | --- |
| 발급·뽑기 연출 | 라운드 완료 → 발급 요청 → 서버 확정 → 결과 표시. 뽑기 연출 방식은 미정 | 요청 중 중복 클릭 차단. isNew 그대로 표시. entryUnlocked=true면 입장 가능 안내·채팅 이동 제공. 자동 입장·연출 중 재발급 없음 |
| 컬렉션 | 인물 10명×스타일 3종, 등급별 장수, 미보유 실루엣·강화 진입 | 미보유도 30종 유지. 전체 미보유·비정상 빈 응답·로딩·조회 실패 구분 |

| 강화 연출·결과 | 서버 성공 뒤 카드가 모여 다음 등급 프레임 공개, 획득 카드·수량·컬렉션 이동 | 조건 충족 시 100% 성공·실패 효과 없음. 한 번에 1회. 다음 강화는 성공 확인 후 새 동작으로 실행 |

강화 비용 표시는 getGameConfig의 현재 upgrade_cost를 사용하며 초기 제품값은 10장입니다. 최종 조건·수량·차감·적립은 RPC가 검증합니다. 기본 강화 연출은 P0, 등급별 연출·건너뛰기·동작 줄이기는 P1로 보강합니다. 일반→레어 약 3초·에픽→스페셜 약 5초를 기준으로 조정합니다. 뽑기 연출과의 효과 공유는 연출 결정 후 검토합니다.

프로필 사진은 인물당 1장으로 카드 이미지와 별개입니다. 목록·방 상단·답변 말풍선은 같은 방 사진을 씁니다. SDK가 프로필 사진→일러스트 카드 이미지 순으로 선택한 표시용 URL을 주고, null 또는 로드 실패 시 이름 첫 글자를 표시합니다. 사진 Storage·RPC는 홍주P, 화면 구현은 자성P입니다.

보유 배지는 버디·이글·알바트로스(P1), 인증 배지는 유튜버·미디어 프로·투어 선수(P2)로 구분해 자산 이름·라벨·사용 예를 제공합니다. 계산은 서버 담당입니다. 위반·제재·재검토, 인증 취소 카드의 발행 중단, 강화로 보유 배지가 오르는 결과 안내는 실서비스 과제로 남깁니다.

### 3.3 요청·오류·화면 수명

1. 새 동작에서 UUID requestId를 만들고 처리 중 버튼을 잠급니다. 성공 확인 뒤 다음 발급/강화만 새 ID, 같은 작업 재전송은 같은 ID·payload입니다.
2. 응답 유실은 결과 미확정으로 표시합니다. 연출 없이 기존 ID로 복구하고 getCollection으로 현재 수량을 확인합니다. 수량만으로 특정 요청의 성공을 단정하지 않습니다. 자동 무한 재시도나 SDK 멱등 보관 기간 밖 작업의 자동 재전송은 하지 않습니다.
3. REQUEST_IN_PROGRESS는 retryAfterMs, INSUFFICIENT_CARDS는 details.missingCards로 'N장 더 필요', MAX_GRADE는 최고 등급을 안내합니다. CONFIG_INVALID는 오류 표시 후 중단하며 임의 기본값으로 요청하지 않습니다.
4. UNAUTHENTICATED는 재로그인, FORBIDDEN은 권한 없음, IDEMPOTENCY_CONFLICT는 작업 연결 오류를 안내합니다. role/userId/보유량 변조·관리 키로 우회하지 않습니다. 브라우저에는 publishable key·사용자 JWT만 둡니다.
5. 성공 후 컬렉션 재조회 실패는 별도로 안내하고 mutation을 다시 실행하지 않습니다. 화면 이탈 뒤 돌아오면 새 동작 전에 수량을 재조회합니다.
6. 계정 전환/로그아웃은 이전 카드·결과·선택·진행 UI를 비웁니다. 늦은 응답·타이머가 새 계정을 덮지 않게 하고 이전 requestId를 새 동작에 재사용하지 않습니다.

## 5. 단계별 실행 순서

### 단계 1 — 입력·더미·디자인 준비

1. `BirdieBuddy-ui`의 기존 레이아웃·공통 UI·라우팅과 루트 SDK export/타입을 대조하고 실제 Auth 및 패키지 통합의 미완료 항목을 기록합니다. 문서에 결정된 정책은 다시 미정으로 돌리지 않습니다.
2. D-01에서 화면 흐름·로딩/빈 상태/오류/권한/미확정, 모바일·키보드·초점·대비·동작 줄이기를 설계합니다. 공유 파일 적용 전 사용자 확인 조건과 자성P 셋업 경계를 지킵니다.
3. D-02에 맞춰 CSS 자리표시자와 가상 데이터 공급부를 준비합니다. isNew와 entryUnlocked의 독립 조합, 미보유·9/10/11장·최고 등급·빈 목록·오류를 포함합니다.
4. 더미는 메모리 상태·새로고침 초기화임을 표시합니다. 추첨·권한·영속 저장·보유 점수 계산을 화면 안에 구현하지 않습니다.

### 단계 2 — A-06 생성·검수·전달

1. 홍주P의 UUID·표시명·유형10행과 5/3/2 구성을 확인합니다. UUID가 없으면 컨셉·규격·생성을 진행하되 UUID를 만들어 최종 매핑으로 전달하지 않습니다.
2. 별도 카드 디자인 프로젝트에서 인물10명과 3스타일의 제작·검수를 진행합니다. 프로젝트 위치·일정·전달 방식은 확인 후 기록합니다.
3. 기본 비율은 가로:세로 2:3이며, 세부 해상도·규격·여백은 별도 프로젝트와 D-02에서 확정합니다. 이름·등급·인증 표시는 UI로 분리하고 인물 잘림·모바일 가독성·스타일 차이·인물 일관성을 검수합니다.
4. MIME·확장자가 일치하는 WebP30개를 준비합니다. PNG로 생성되면 변환 후 확인합니다. UUID·스타일·다운로드 가능한 WebP URL30행을 홍주P 인계 자료로 제공합니다. 로컬 경로·접근 불가 URL은 전달 완료로 표시하지 않습니다. 전달 위치·권한이 없으면 파일은 보존하고 전달만 대기로 남깁니다.
5. 임시 URL의 유효 시점·대응 파일을 기록합니다. 별도 지시 없이 외부 메시지를 전송하지 않습니다. 홍주P가 card-assets의 `<influencer_uuid>/<style>.webp`에 저장하고 DB에는 image_path를 넣습니다. 현호P는 SDK imageUrl로 30개 표시를 확인합니다.
6. 이미지 지연 시 자리표시자로 UI 구현을 계속하되 A-06 완료로 표시하지 않습니다. 사진 업로드 시연 샘플은 생성한 가상 인물 이미지에서 준비합니다.

### 단계 3 — P0 구현·SDK 통합

1. D-03과 D-06을 연결해 요청·응답·결과 상태를 분리하고, D-07·D-08을 같은 데이터 공급부에 연결합니다. D-04 연출은 확정됐으며(2026-11-13) 새 3등급 SDK 뒤 `/draw`에 적용합니다.

3. 실제 lib/api 연결 후 templateId·grade·최신 수량/비용을 확인합니다. 같은 ID 복구·성공 뒤 재조회·계정 변경 처리를 적용합니다. 없는 entryUnlocked를 false로 가정해 실제 연동 완료로 표시하지 않습니다.

## 7. 현재 이어서 할 일 (2026-11-12)

1. 자성P와 `/home`·`/draw` 경로, 입장 가능 안내의 채팅 이동, 별도 프론트 패키지 유지 및 실제 Auth/SDK 연결 경계를 합의합니다. 기존 목업과 디자인 시스템을 기준으로 작업합니다.
2. 별도 카드 디자인 프로젝트에서 2:3을 기준으로 D-02 세부 규격과 10명×3스타일 A-06 최종 이미지를 제작·검수합니다. 기존 30개 fixture를 최종 산출물로 취급하지 않습니다. UUID·Storage 전달 방식은 홍주P와 확인합니다.
3. 목업을 발급 요청·결과, 30종 컬렉션, 강화 확인·결과 화면으로 교체합니다. 실제 `lib/api` 타입과 인증 공급부를 연결하고 §3.3의 중복 요청·결과 미확정·계정 전환을 처리합니다.
4. 보유 카드·상세와 배지, 등급별 연출을 보강하고 자성P 화면에 인계합니다. 실제 SDK·이미지·모바일 접근성·오류 복구를 §5 기준으로 검증합니다.

이번 갱신은 저장소와 다른 담당 문서의 정적 대조입니다. 카드 화면·실제 SDK 연동·최종 이미지·원격 환경은 이번에 실행하거나 검증하지 않았습니다.
