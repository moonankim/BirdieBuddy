# BirdieBuddy — 현호P 작업 계획

**역할:** 카드 뽑기·결과·컬렉션·강화 UI 구현 및 전체 화면 디자인

**문서 기준일:** 2026-11-10

**공통 기준:** [전체 시스템 아키텍처](./architecture.md) · [백엔드·SDK 계약](./홍주P_plan.md) · [U-01 시연·발표 계획](./anonymous-plan.md)

이 문서는 현호P의 실행 계획입니다. 공통 구조·담당 경계는 architecture.md, 데이터·권한·SDK·게임 설정의 상세 계약은 홍주P_plan.md §§4~7, 시연·인계 기준은 anonymous-plan.md를 참조합니다. 문서 정리는 코드 구현 착수나 완료를 의미하지 않으며, 실제 구현은 사용자의 별도 요청 후 진행합니다. 앱·supabase/·환경 파일·발표 파일을 이번 문서 갱신으로 미리 만들지 않습니다.

## 1. 목표와 담당 경계

우선 목표는 더미 카드를 이용해 **라운드 완료 → 카드팩 개봉 → 결과 → 컬렉션 → 강화** 흐름을 구현하고, 의존성이 준비되면 실제 API로 연결하는 것입니다. 실제 카드 이미지는 생성 후 교체합니다.

| 구분 | 현호의 작업 | 경계 |
| --- | --- | --- |
| 직접 구현 | 뽑기·결과 화면, 컬렉션·강화 화면, 카드·카드팩·등급 효과 | `app/(user)/draw/`, `app/(user)/collection/`, `components/card/` |
| 디자인 제공 | 전체 화면 시안, 카드 스타일 가이드, 공통 디자인 토큰 제안 | 채팅·인박스·관리자 화면의 구현은 자성P 담당 |
| 협의 후 반영 | 공통 UI 디자인 적용, 공통 레이아웃과의 연결 | `components/ui/` 등 공유 파일 수정은 사용자 확인 후 진행 |
| 다른 담당자 영역 | 프로젝트 셋업·계정 전환, API·DB·시드·배포, AI·이미지 생성 | 현호가 대신 구현하거나 설정을 변경하지 않음 |

새 의존성 설치, 프로젝트 설정 변경, 다른 담당자의 파일 수정이 필요하면 대상과 이유를 사용자에게 먼저 설명하고 확인받습니다. 담당 경로에 기존 코드가 생긴 경우에도 내용을 확인한 후 필요한 부분만 변경합니다.

## 2. 현재 상태와 착수 조건

문서 기준일의 저장소에는 README와 계획 문서만 있으며, 실행 가능한 앱 골격과 SDK 코드는 없습니다. 공통 문서의 폴더 구조는 개발 착수 시 생성할 예정 구조입니다. 아래의 실제 연결·전달 여부는 확인하되, 문서에 정해진 계약을 미정으로 되돌리지 않습니다.

| 필요한 입력 | 관련 담당 | 사용자에게 확인할 내용 | 준비 전 가능한 작업 |
| --- | --- | --- | --- |
| 프로젝트 골격 F-01 | 자성P | 골격 전달 여부, 기존 스타일·라우팅·공통 레이아웃 사용법. 없으면 별도 작업 방식 확인 | 화면 구성·상태·산출물 정의 |
| 카드 SDK B-03·B-04, 설정 B-03·B-10, 계약 T-01 | 홍주P | lib/api 구현·타입·오류·설정 조회의 연결 상태 | 골격 확보 후 계약에 맞춘 현호 영역 내부 더미로 UI 구현 |
| 데모 계정 연결 F-02·B-02 | 자성P·홍주P | 실제 Auth 로그인/로그아웃과 세션 변경 알림, 데모 권한 확인 방법 | 가상 사용자 한 명의 더미 시나리오 정의 |
| 실제 인물·아트 확정 T-02 | 전원 | 실제 인물·최종 아트 확정 여부. 스타일·유형 코드는 아래 기본값 사용 | 가상 인물 10명·3종 스타일·자리표시자로 독립 개발 |
| 카드 이미지 A-06 | 문환P | 리소스 전달 위치, 템플릿과 이미지 매핑, 이미지 규격 | CSS 더미 카드로 기능 검증 |

**확인 원칙:** 기존 문서와 전달된 구현에서 확인할 수 있는 계약을 먼저 사용하고, 없는 골격·연결 정보나 결과가 크게 달라지는 미확정 사항만 사용자에게 확인합니다. 의존성이 없는 설계·더미 작업은 진행할 수 있습니다. 다른 담당자에게 임의로 연락하거나 담당 범위를 대신 수행하지 않습니다.

독립 개발 기본값은 등급 `common→rare→epic→special`, 스타일 `illust/retro/holo`, 유형 `youtuber/media_pro/tour`입니다. 실제 인물·최종 아트는 임의로 확정하지 않습니다. 배지 표시는 `verifiedAt`과 `influencerType`을 기준으로 자성P 화면에 연결하며, 유형만으로 인증 완료를 표시하지 않습니다.

### 현호가 사용할 SDK

| SDK | UI에서 사용하는 목적 | 적용 계약 |
| --- | --- | --- |
| `completeRound({requestId, demoForceGrade?})` | 라운드 완료와 카드 결과 수신 | `complete_round` RPC. roundId·drawId·grade·template·isNew·ownedCount 사용. 고정 등급은 데모 capability 필요 |
| `getCollection()` | 보유 현황 조회·갱신 | `collection_view`의 미보유 포함 30개 항목. template·등급별 counts·totalCards·highestGrade 사용 |
| `upgradeCard({requestId, templateId, grade})` | 선택 카드 강화 | `upgrade_card` RPC. fromGrade·toGrade·consumed·remainingCount·upgradedCount 사용 |
| `getGameConfig()` | 현재 강화 비용·게임 설정 조회 | key/value/version 사용. 조회만 연결하고 관리자 설정 변경은 담당하지 않음 |

상태가 있는 화면은 client component로 만들고 브라우저의 `lib/api` export를 사용합니다. SDK의 `createBackendApi(client)`·Supabase 연결·타입 정규화는 홍주P 영역입니다. Next.js 서버 컴포넌트는 정적 shell만 맡으며 Server Actions·API Routes·Route Handlers나 별도 서버를 추가하지 않습니다.

SDK 반환은 `Result<T>`로 처리하고 actor는 실제 Auth 세션에서 얻습니다. 화면에서 userId·role·보유량을 요청 인자로 보내 권한을 결정하지 않습니다. 카드의 `imageUrl`은 SDK가 Storage 경로에서 생성한 값을 사용하며 환경별 절대 URL을 하드코딩하지 않습니다. 브라우저에는 publishable key·사용자 JWT만 사용합니다.

모든 mutation은 UUID `requestId`를 사용합니다. 새 사용자 동작은 새 ID, 응답 유실 등 같은 작업의 네트워크 재전송은 같은 ID·payload를 유지합니다. `REQUEST_IN_PROGRESS`는 `retryAfterMs`를 따르고, `IDEMPOTENCY_CONFLICT`는 입력·작업 연결 오류로 표시합니다. `UNAUTHENTICATED`는 재로그인을 안내하고 `FORBIDDEN`을 임의 역할 변경으로 우회하지 않습니다. 자동 무한 재시도나 실패 후 더미 성공 처리는 하지 않습니다.

API·DB 계약은 새로 정의하지 않습니다. 더미 공급부도 공개 도메인 타입을 기준으로 하되, 그 내부 상태·동작은 백엔드 구현이나 실제 연동 완료로 취급하지 않습니다.

## 4. 단계별 실행 순서

### 단계 1 — 화면과 더미 설계

1. D-01에서 카드 화면의 구성과 사용자 행동, 각 화면의 로딩·빈 상태·오류 상태를 정리합니다.
2. D-02에서 이름·스타일·등급을 텍스트로 구분하는 단순 CSS 카드와 실루엣을 준비합니다. 색상만으로 등급을 전달하지 않습니다.
3. 가상 인물 10명 × 스타일 3종의 더미 데이터를 설계합니다. 신규·중복, 미보유, 강화 가능·불가, 최고 등급 사례를 포함합니다.
4. 이미지 영역은 데이터의 이미지 주소를 받아 표시하도록 설계하고, 주소가 없거나 로딩이 실패하면 자리표시자를 유지합니다.

실제 인물·최종 이미지·스타일은 임의로 확정하지 않습니다. 프로젝트 골격이 없으면 이 단계의 설계까지 진행하고 구현 방식은 사용자에게 확인합니다.

### 단계 2 — 더미 기반 P0 구현

골격 또는 별도 작업 방식을 확인받은 뒤 진행합니다.

1. 현호 영역 안에 카드 표시 컴포넌트와 더미 데이터 공급부를 둡니다. 화면과 데이터 공급부를 분리해 이후 실제 API로 교체할 수 있게 합니다.
2. D-03·D-04·D-06을 연결합니다: **대기 → 요청 중 → 카드팩 등장 → 개봉 → 단계 공개 → 결과**.
3. 요청 실패 시 오류를 표시하고 재시도 기회를 제공합니다. 실제 요청의 응답이 유실되면 결과 미확정으로 표시하고 같은 requestId·payload로 복구합니다. 결과 확인 전 새 뽑기·강화를 실행해 중복 처리하지 않습니다.
4. D-07 컬렉션과 D-08 강화를 구현합니다. 더미 뽑기·강화 결과를 같은 더미 보유 상태에 반영해 화면 간 일관성을 확인합니다.
5. 더미 동작은 메모리 상태로 제한하고 새로고침 시 초기화됨을 시연 설명에 명시합니다. 백엔드 추첨·영속 저장·확률 로직은 구현하지 않습니다.

강화 조건은 공통 기준을 참조합니다. 초기 기본값은 같은 template·grade 10장으로 다음 grade 1장이며 special은 강화할 수 없습니다. 테스트용 값은 더미 공급부에만 두고, 실제 화면은 getGameConfig의 현재 upgrade_cost로 가능 여부를 안내합니다. 최종 보유량·규칙 검증과 차감·적립은 RPC가 맡습니다.

### 단계 3 — 실제 API 연결과 P0 통합

1. T-01의 SDK 타입·오류와 F-02의 실제 Auth 세션 변경 연결을 확인합니다. 문서와 구현이 다르면 차이를 확인한 후 연결하며 화면에서 계약을 새로 만들지 않습니다.
2. 현호 영역의 데이터 연결부에서 더미를 lib/api 호출로 교체하고 Result의 성공·오류를 처리합니다. 실패 시 더미 성공으로 대체하지 않습니다.
3. 뽑기 결과의 isNew는 응답을 사용합니다. 이는 추첨 직전 해당 template을 등급 무관하게 현재 0장 보유했는지이며 과거 수집 이력이 아닙니다. 카드 이미지가 아직 없어도 자리표시자는 유지할 수 있습니다. 뽑기 성공 후 컬렉션도 다시 조회합니다.
4. 강화 성공 후 컬렉션을 다시 조회해 보유 수량을 갱신합니다. 강화 성공과 후속 조회 실패를 구분해 안내하고, 조회 실패 때문에 강화를 다시 요청하지 않습니다.
5. 로그아웃·계정 전환 시 이전 사용자의 카드·결과·진행 중 작업 상태를 비우고 새 세션으로 다시 조회합니다. 이전 요청의 늦은 응답이 새 사용자의 화면을 덮거나 이전 requestId가 새 계정 동작에 재사용되지 않도록 합니다.
6. INSUFFICIENT_CARDS는 details의 requiredCards·ownedCards·missingCards로 안내하고 현재 컬렉션·설정을 재조회합니다. MAX_GRADE는 실행 불가로 표시합니다. 확정된 실패에 성공 연출이나 임의 수량 변경을 적용하지 않습니다. 응답 유실은 실패로 단정하지 않고 기존 ID로 결과를 복구합니다.
7. 실제 데이터로 뽑기 → 결과 → 컬렉션 → 강화 흐름을 검증하고 T-03 통합 참여 자료를 준비합니다. SDK 로컬 검증과 담당 화면·배포 URL 통합 결과는 별도로 기록합니다.

**D-08 강화를 P0 통합 전에 완료합니다.** 기존의 ‘P0 통합 후 밤에 강화 구현’ 순서 대신, 강화 완료 → 통합 검증 순서를 따릅니다. 실제 배포와 환경 구성은 홍주P 담당입니다.

### 단계 4 — 추가 연출·배지·실제 이미지 적용

1. P0 흐름이 완성되면 D-05 특수 연출·건너뛰기를 추가합니다.
2. D-09 배지 3종과 표시 용례를 준비합니다.
3. 이미지 리소스가 제공되면 사용자에게 매핑·규격을 확인받고 임시 이미지 입력을 교체합니다. 문환P의 생성 작업이나 홍주P의 시드·스토리지 작업은 대신 수행하지 않습니다.
4. 최종 프레임·스타일을 다듬고 카드 잘림, 비율, 글자 가독성, 이미지 실패 시 대체 표시를 재검증합니다.

### 단계 5 — U-01 시연 연결과 인계

실제 이미지 전달을 기다리지 않고, P0 통합과 P1 데모 옵션이 준비되면 자리표시자 상태로도 진행합니다.

1. P1의 D-05에서 권한 있는 데모 계정이 `completeRound({requestId, demoForceGrade: 'special'})`을 사용하는 시연 UI를 연결합니다. capability 부여·데모 계정 준비는 홍주P 담당이며 화면의 옵션 숨김만으로 권한을 보장하지 않습니다. 일반 계정의 FORBIDDEN 응답도 처리합니다.
2. 고정 대상은 special 등급뿐입니다. 인물·스타일은 무작위이고 isNew도 실제 결과대로 표시합니다. 라운드 완료 버튼은 실제 골프존 연동이 아닌 데모임을 설명하며, 새 requestId의 새 동작은 새 라운드입니다. 시연 UI 미연결을 반복 추첨으로 대신하지 않습니다.
3. U-01 본 대본의 0:30~1:15에 맞춰 라운드 완료 → 스페셜 연출 → 컬렉션 확인 흐름과 건너뛰기를 검증합니다. 강화는 P0 구현·통합 범위에 유지하되 발표에서는 현재 동일 template·grade 수량과 비용이 충족된 경우에만 보조 시연합니다.
4. 기본 setup은 userA 첫 인물 카드 12장·userB 5장과 첫 방 active 상태를 예정합니다. 반복 시연 시 현재 상태를 확인하며, 방금 뽑은 카드 한 장으로 특정 방이 해금됐다고 설명하지 않습니다. 이후 기존 첫 방을 여는 화면은 자성P 담당입니다. 강화 뒤 장수가 줄어도 기존 active가 유지되는 정책과도 맞춥니다.
5. 담당 미정인 U-01에 사용할 화면·환경/버전·계정 역할·현재 카드 수량/설정·연출 소요 시간·검증 결과·자리표시자 여부·남은 한계를 인계 자료로 정리합니다. 암호·JWT·관리 키는 기록하지 않습니다. 카드 획득으로 기존 질문의 score snapshot이 재계산됐다고 설명하지 않습니다.
6. T-05 기능 동결 후 전체 2회 리허설에 카드 화면 결과·오류·수정 및 재검증 자료를 제공합니다. 발표 파일·리허설 기록 작성은 U-01 담당이며 현호P가 대신 맡거나 담당자를 임의로 확정하지 않습니다. setup 재실행을 초기화로 간주하지 않고, 필요한 로컬 reset+setup은 홍주P의 준비 절차를 따릅니다.

## 5. 검증과 완료 판단

구현 요청 후 프로젝트에 마련된 검사 명령을 확인하여 변경 위험도에 맞게 타입·린트·빌드 및 필요한 테스트를 수행합니다. 개발 서버나 브라우저는 사용자 요청 없이 실행하지 않습니다. 사용자가 이미 실행한 서버가 있으면 비대화형·headless 검증을 활용할 수 있습니다.

| 검증 대상 | 확인할 시나리오 |
| --- | --- |
| 뽑기·결과 | 각 등급, 현재 보유 기준 isNew, 요청 실패·응답 유실, 연속 클릭, 같은 requestId 재전송 시 중복 지급 없음, 단계 공개 순서, 결과 일관성 |
| 건너뛰기·동작 줄이기 | 공개 중 건너뛰어도 같은 카드 표시, 요청 재실행 없음, 과도한 모션 생략 |
| 컬렉션 | 미보유 포함 30개 항목·등급별 0장, 전체 미보유와 비정상 빈 응답 구분, 로딩·조회 실패, 인물·스타일·등급별 수량 |
| 강화 | 현재 비용 직전·일치·초과, 최고 등급, 서로 다른 템플릿·등급의 수량을 합산하지 않음, 중복 클릭, 확정 실패 시 성공 연출 없음, 응답 유실은 같은 ID로 복구 |
| 갱신·계정 전환 | 성공 후 수량 일치, 강화 성공 후 조회만 실패한 경우, 이전 계정 응답의 뒤늦은 도착 |
| 카드 리소스 | 이미지 주소 없음·로드 실패·정상 이미지, 긴 이름, 이미지 교체 후 레이아웃 유지 |
| 사용성 | 모바일 폭, 키보드로 버튼 조작, 초점 표시, 등급의 텍스트 구분, 동작 줄이기 설정 |
| 데모·인계 | 허용 계정의 special 고정·일반 계정 거부, 인물·스타일 무작위 유지, 건너뛰기 후 같은 결과, 45초 카드 흐름, 현재 상태·placeholder·미검증 범위 표시 |

더미 시나리오 검증은 UI 진행 상태의 근거로 기록합니다. API 의존 티켓의 최종 완료는 실제 연동 검증 후 판단합니다. 최종 아트와 실제 이미지 적용은 더미 UI 검증과 별도 기록합니다. 실행하지 못한 검증은 이유와 함께 남기며 실제 검증 없이 완료 처리하지 않습니다.

## 6. 인계 산출물과 보류 사항

| 대상 | 준비할 산출물 | 전달·적용 조건 |
| --- | --- | --- |
| 자성P | D-01 전체 화면 시안, 공통 디자인 토큰 제안, D-09 SVG와 사용 예 | 공유 파일 적용은 사용자 확인 후. 화면 구현·인증 연결은 자성P 담당 |
| 문환P | D-02 스타일 가이드, 이미지 영역 규격·여백·매핑 요구 | T-02 및 실제 이미지 작업 재개를 사용자에게 확인 |
| 홍주P | cards·game-config SDK의 계약과 구현 차이, 오류·멱등 복구·계정 전환 검증 결과, 데모 옵션 연결 상태 | 홍주P 계획의 SDK 계약 사용. 서버·capability·시드·Storage 구성은 홍주P 담당 |
| U-01 담당 미정 | 카드 시연 조작 순서·소요 시간, 환경/버전·현재 카드/설정, 캡처와 검증 근거·남은 한계 | 실제 화면 통합 후 인계. 강화는 보조 시연이며 최종 장표·전체 리허설 기록은 U-01 담당 |
| 사용자 | 티켓별 진행 상태, 더미/실제 연동 검증 결과, 차단된 의존성과 필요한 입력 | 구현 단계마다 확인 필요 사항을 구체적으로 보고 |

현재는 **계획 갱신 상태**입니다. 실제 착수·연결을 기다리는 항목은 F-01 골격·F-02 Auth 세션 연결, B-03·B-04·game-config SDK 구현, 데모 capability와 시연 UI 연결, 실제 인물·최종 아트·이미지 리소스입니다. 스타일·유형 코드와 SDK 계약은 위 기준을 사용합니다. 더미 UI·SDK 로컬 검증·팀 화면 통합·실제 이미지 적용·원격 배포·전체 리허설을 각각 구분하며, 이번 갱신을 구현·검증 완료로 표시하지 않습니다.
