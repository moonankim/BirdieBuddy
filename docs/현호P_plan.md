# BirdieBuddy — 현호P 작업 계획

**역할:** 카드 뽑기·결과·컬렉션·강화 UI 구현 및 전체 화면 디자인

**문서 기준일:** 2026-11-09

**공통 기준:** [전체 시스템 아키텍처](./architecture.md)

이 문서는 현호P의 실행 계획입니다. 기술 스택, DB, 공통 개발 규칙, 게임 설정과 전체 API 명세는 공통 기준 문서를 참조합니다. 문서 정리는 코드 구현 착수나 완료를 의미하지 않으며, 실제 구현은 사용자의 별도 요청 후 진행합니다.

## 1. 목표와 담당 경계

우선 목표는 더미 카드를 이용해 **라운드 완료 → 카드팩 개봉 → 결과 → 컬렉션 → 강화** 흐름을 구현하고, 의존성이 준비되면 실제 API로 연결하는 것입니다. 실제 카드 이미지는 생성 후 교체합니다.

| 구분 | 현호의 작업 | 경계 |
| --- | --- | --- |
| 직접 구현 | 뽑기·결과 화면, 컬렉션·강화 화면, 카드·카드팩·등급 효과 | `app/(user)/draw/`, `app/(user)/collection/`, `components/card/` |
| 디자인 제공 | 전체 화면 시안, 카드 스타일 가이드, 공통 디자인 토큰 제안 | 채팅·인박스·관리자 화면의 구현은 자성P 담당 |
| 협의 후 반영 | 공통 UI 디자인 적용, 공통 레이아웃과의 연결 | `components/ui/` 등 공유 파일 수정은 사용자 확인 후 진행 |
| 다른 담당자 영역 | 프로젝트 셋업·계정 전환, API·DB·시드·배포, AI·이미지 생성 | 현호가 대신 구현하거나 설정을 변경하지 않음 |

새 의존성 설치, 프로젝트 설정 변경, 다른 담당자의 파일 수정이 필요하면 대상과 이유를 사용자에게 먼저 설명하고 확인받습니다. 담당 경로에 기존 코드가 생긴 경우에도 내용을 확인한 후 필요한 부분만 변경합니다.

## 2. 현재 상태와 착수 조건

문서 기준일의 저장소에는 README와 계획 문서·HTML만 있으며, 실행 가능한 앱 골격과 API 코드는 없습니다. 아래의 미확정 항목은 승인된 것으로 간주하지 않습니다.

| 필요한 입력 | 관련 담당 | 사용자에게 확인할 내용 | 준비 전 가능한 작업 |
| --- | --- | --- | --- |
| 프로젝트 골격 F-01 | 자성P | 골격 전달 여부, 기존 스타일·라우팅·공통 레이아웃 사용법. 없으면 별도 작업 방식 확인 | 화면 구성·상태·산출물 정의 |
| 카드 API B-03·B-04, 계약 T-01 | 홍주P | 요청·응답 JSON, 오류 형식, 사용자 식별 방법, 설정값 전달 방식 | 골격 확보 후 현호 영역 내부 더미로 UI 구현 |
| 데모 계정 연결 F-02 | 자성P | 화면에서 현재 사용자를 받는 방법, 계정 변경 시 갱신 방법 | 가상 사용자 한 명의 더미 시나리오 정의 |
| 인물·스타일 확정 T-02 | 전원 | 확정된 인물과 스타일, 카드 정보 중 ‘유형’의 표시 의미 | 가상 인물명·임시 스타일 표시와 자리표시자 준비 |
| 카드 이미지 A-06 | 문환P | 리소스 전달 위치, 템플릿과 이미지 매핑, 이미지 규격 | CSS 더미 카드로 기능 검증 |

**확인 원칙:** 의존성이 필요한 단계에 도달하면 사용자에게 필요한 입력과 선택지를 확인합니다. 확인 전에는 해당 연결 작업을 보류하고, 의존성이 없는 설계·더미 작업만 진행합니다. 다른 담당자에게 임의로 연락하거나 담당 범위를 대신 수행하지 않습니다.

### 현호가 사용할 API

| API | UI에서 사용하는 목적 | 연동 전 확인할 계약 |
| --- | --- | --- |
| `POST /api/rounds/complete` | 라운드 완료 요청과 카드 결과 수신 | 사용자 식별, 카드·인물·등급·신규 여부, 실패·중복 요청 처리 |
| `GET /api/me/collection` | 보유 현황 조회·갱신 | 템플릿 목록과 미보유 정보, 등급별 수량, 이미지 주소, 강화 조건의 전달 방법 |
| `POST /api/cards/upgrade` | 선택 카드 강화 | 템플릿·등급 지정 방식, 성공 응답, 수량 부족·최고 등급 등 오류 |

API는 사용만 하며 새 엔드포인트나 DB 스키마를 정의하지 않습니다. 더미용 화면 데이터 형식은 임시 내부 형식으로 표시하고 실제 API 계약으로 취급하지 않습니다.

## 4. 단계별 실행 순서

### 단계 1 — 화면과 더미 설계

1. D-01에서 카드 화면의 구성과 사용자 행동, 각 화면의 로딩·빈 상태·오류 상태를 정리합니다.
2. D-02에서 이름·스타일·등급을 텍스트로 구분하는 단순 CSS 카드와 실루엣을 준비합니다. 색상만으로 등급을 전달하지 않습니다.
3. 가상 인물 10명 × 스타일 3종의 더미 데이터를 설계합니다. 신규·중복, 미보유, 강화 가능·불가, 최고 등급 사례를 포함합니다.
4. 이미지 영역은 데이터의 이미지 주소를 받아 표시하도록 설계하고, 주소가 없거나 로딩이 실패하면 자리표시자를 유지합니다.

실제 인물·최종 이미지·스타일은 임의로 확정하지 않습니다. 프로젝트 골격이 없으면 이 단계의 설계까지 진행하고 구현 방식은 사용자에게 확인합니다.

### 단계 2 — 더미 기반 P0 구현

골격 또는 별도 작업 방식을 확인받은 뒤 진행합니다.

1. 현호 영역 안에 카드 표시 컴포넌트와 더미 데이터 공급부를 둡니다. 화면과 데이터 공급부를 분리해 이후 실제 API로 교체할 수 있게 합니다.
2. D-03·D-04·D-06을 연결합니다: **대기 → 요청 중 → 카드팩 등장 → 개봉 → 단계 공개 → 결과**.
3. 요청 실패 시 오류를 표시하고 재시도 기회를 제공합니다. 전송 결과가 불확실한 실제 요청은 계약 확인 없이 자동 재전송하지 않습니다.
4. D-07 컬렉션과 D-08 강화를 구현합니다. 더미 뽑기·강화 결과를 같은 더미 보유 상태에 반영해 화면 간 일관성을 확인합니다.
5. 더미 동작은 메모리 상태로 제한하고 새로고침 시 초기화됨을 시연 설명에 명시합니다. 백엔드 추첨·영속 저장·확률 로직은 구현하지 않습니다.

강화 조건은 공통 기준을 참조합니다. 테스트용 값은 더미 공급부에만 두고, 실제 화면은 확인된 데이터·설정 계약을 통해 조건을 받도록 연결합니다.

### 단계 3 — 실제 API 연결과 P0 통합

1. 사용자에게 카드 API 계약·현재 사용자 전달 방식·강화 설정값 전달 방식을 확인받습니다.
2. 현호 영역의 데이터 연결부에서 더미를 실제 API 호출로 교체합니다. 실패 시 더미 성공으로 대체하지 않습니다.
3. 뽑기 결과의 신규 여부는 응답을 사용합니다. 카드 이미지가 아직 없어도 더미 이미지 표현은 유지할 수 있습니다.
4. 강화 성공 후 컬렉션을 다시 조회해 보유 수량을 갱신합니다. 강화 성공과 후속 조회 실패를 구분해 안내하고, 조회 실패 때문에 강화를 다시 요청하지 않습니다.
5. 계정 전환 연동 시 이전 사용자의 카드 상태를 비우고 다시 조회합니다. 이전 요청의 늦은 응답이 새 사용자의 화면을 덮지 않도록 합니다.
6. 실제 데이터로 뽑기 → 결과 → 컬렉션 → 강화 흐름을 검증하고 T-03 통합 참여 자료를 준비합니다.

**D-08 강화를 P0 통합 전에 완료합니다.** 기존의 ‘P0 통합 후 밤에 강화 구현’ 순서 대신, 강화 완료 → 통합 검증 순서를 따릅니다. 실제 배포와 환경 구성은 홍주P 담당입니다.

### 단계 4 — 추가 연출·배지·실제 이미지 적용

1. P0 흐름이 완성되면 D-05 특수 연출·건너뛰기를 추가합니다.
2. D-09 배지 3종과 표시 용례를 준비합니다.
3. 이미지 리소스가 제공되면 사용자에게 매핑·규격을 확인받고 임시 이미지 입력을 교체합니다. 문환P의 생성 작업이나 홍주P의 시드·스토리지 작업은 대신 수행하지 않습니다.
4. 최종 프레임·스타일을 다듬고 카드 잘림, 비율, 글자 가독성, 이미지 실패 시 대체 표시를 재검증합니다.

## 5. 검증과 완료 판단

구현 요청 후 프로젝트에 마련된 검사 명령을 확인하여 변경 위험도에 맞게 타입·린트·빌드 및 필요한 테스트를 수행합니다. 개발 서버나 브라우저는 사용자 요청 없이 실행하지 않습니다. 사용자가 이미 실행한 서버가 있으면 비대화형·headless 검증을 활용할 수 있습니다.

| 검증 대상 | 확인할 시나리오 |
| --- | --- |
| 뽑기·결과 | 각 등급, 신규/중복, 요청 실패, 연속 클릭, 단계 공개 순서, 결과 일관성 |
| 건너뛰기·동작 줄이기 | 공개 중 건너뛰어도 같은 카드 표시, 요청 재실행 없음, 과도한 모션 생략 |
| 컬렉션 | 보유·미보유, 데이터 없음, 로딩·조회 실패, 인물·스타일·등급별 수량 |
| 강화 | 필요 수량 직전·일치·초과, 최고 등급, 서로 다른 템플릿·등급의 수량을 합산하지 않음, 중복 클릭, 실패 시 수량 유지 |
| 갱신·계정 전환 | 성공 후 수량 일치, 강화 성공 후 조회만 실패한 경우, 이전 계정 응답의 뒤늦은 도착 |
| 카드 리소스 | 이미지 주소 없음·로드 실패·정상 이미지, 긴 이름, 이미지 교체 후 레이아웃 유지 |
| 사용성 | 모바일 폭, 키보드로 버튼 조작, 초점 표시, 등급의 텍스트 구분, 동작 줄이기 설정 |

더미 시나리오 검증은 UI 진행 상태의 근거로 기록합니다. API 의존 티켓의 최종 완료는 실제 연동 검증 후 판단합니다. 최종 아트와 실제 이미지 적용은 더미 UI 검증과 별도 기록합니다. 실행하지 못한 검증은 이유와 함께 남기며 실제 검증 없이 완료 처리하지 않습니다.
