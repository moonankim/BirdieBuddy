# main 병합 후 담당자 영향 확인 지침

BirdieBuddy에서 `main`/`origin/main`의 변경을 현재 작업 브랜치에 병합할 때 아래 절차를 함께 수행한다. 사용자가 병합을 요청하면 PR·커밋 영향 검토와 분명한 홍주P 후속 변경까지 같은 작업 범위로 본다.

## 절차

1. **작업 트리와 기준점을 확인한다.** 기존 변경을 보존하고 원격 `main`을 갱신한다. 현재 브랜치와 `origin/main`의 merge base, 양쪽 전용 커밋, 이미 반영된 변경을 확인한다.
2. **등록된 PR과 각 커밋을 읽는다.** merge commit을 PR에 연결하고 PR의 목적·설명·담당자 인계·검증 결과를 확인한다. 각 커밋의 본문·변경 파일·diff도 확인하며 제목만으로 판단하지 않는다.
3. **담당 경계에 따라 영향을 분류한다.** PRD, 공통 아키텍처, 역할별 계획, 현재 코드·DB·SDK 계약을 대조한다. 명확한 홍주P backend/SDK 후속 수정은 같은 작업에서 구현한다. 다른 담당자의 계획·코드는 직접 의존이 필요한 경우에만 건드리고 나머지는 소유자별 후속 요청으로 기록한다.
4. **미확정 정책은 구현으로 굳히지 않는다.** 제안, 담당자 한 명의 동의, 제품 확정을 구분한다. 제품·공동 담당자 결정이 필요한 schema·보상·이관은 기존 동작과 데이터를 보존하고, 결정 내용·필요한 담당자·막혀 있는 구현을 기록한다.
5. **계약 문서를 함께 갱신한다.** `docs/홍주P_plan.md`의 최신 날짜 항목에 merge SHA, PR 번호와 commit, 파일/담당 영향, 수행한 변경, 후속 담당자, 검증 범위와 미검증 사항을 남긴다. `docs/architecture.md`의 공통 상태와 소유 경계도 같은 결론으로 맞춘다. 정기적으로 재사용할 절차는 이 문서에 반영한다.
6. **검증 증거의 출처를 분리한다.** upstream PR의 CI 결과는 그 PR에서 보고된 결과로만 적고 현재 브랜치에서 다시 실행한 것으로 표시하지 않는다. 변경 종류와 요청 범위에 필요한 검증만 수행한다. runtime·DB·Function 검증이나 변경이 있으면 `harness/verification-log.md`에 환경과 증거를 기록한다. 미실행 검증은 이유와 남은 범위를 명시한다.
7. **병합을 마무리하고 상태를 보고한다.** 충돌이 있으면 작업 트리 변경을 보존하며 해결한다. 병합과 후속 변경은 로컬에 유지하고, push는 사용자가 요청한 경우에만 한다. 결과에는 merge SHA, PR·commit, 실제 수정과 보류 정책, 검증 한계를 요약한다.

## 이번 저장소에서 유지할 경계

- backend와 SDK의 실행 기준은 `docs/홍주P_plan.md`, 공통 구조와 담당자는 `docs/architecture.md`, 제품 동작은 `docs/prd.md`를 따른다.
- Supabase 정책이 확정되지 않았으면 schema·migration·실제 데이터를 추정해 바꾸지 않는다. 확정된 일반 backend 변경은 루트 `AGENTS.md`의 hosted 동기화 지침과 검증 절차를 따른다.
- 다른 담당자의 UI·AI 구현을 홍주P 소유 산출물로 취급하지 않는다. PR 설명에 인계가 있으면 변경 여부와 필요한 다음 담당자를 구분해 기록한다.
